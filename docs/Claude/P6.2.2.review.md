## 一、代码 Bug

### 🔴 BUG-H1 `policy.rs` — `SCHED_FLAG_UTIL_CLAMP*` 常量值全部错误，uclamp 实际从未生效

**这是 NEW-H2（uclamp 全链路补齐）最终仍未闭合的致命缺口。**

```rust
// 代码里的错误值
const SCHED_FLAG_UTIL_CLAMP: u64 = 0x4000_0000;
const SCHED_FLAG_UTIL_CLAMP_MIN: u64 = 0x0000_0001;
const SCHED_FLAG_UTIL_CLAMP_MAX: u64 = 0x0000_0002;
```

Linux 5.10（SM8550/SM8650 目标内核）的 `include/uapi/linux/sched.h` 实际值：

```c
#define SCHED_FLAG_UTIL_CLAMP_MIN   0x20
#define SCHED_FLAG_UTIL_CLAMP_MAX   0x40
#define SCHED_FLAG_UTIL_CLAMP       0x60   // MIN | MAX
```

结果：`attr.sched_flags = 0x4000_0000 | 0x01 | 0x02 = 0x40000003`，内核遇到未知 flag 位，`sched_setattr` 返回 `EINVAL`。`apply_uclamp` 触发 `warn_once` 写 audit，但 uclamp 值**从未写入内核**。

数据管道（config → PolicyModel → Policy → apply_uclamp syscall）现在结构正确，但终端调用使用了错误的协议。相当于把正确的数据通过错误的网线插口发出去。

**修复：**
```rust
const SCHED_FLAG_UTIL_CLAMP_MIN: u64 = 0x20;
const SCHED_FLAG_UTIL_CLAMP_MAX: u64 = 0x40;
const SCHED_FLAG_UTIL_CLAMP: u64 = 0x60;
```

### 🟠 BUG-M1 `policy.rs::apply_thread` — Exited 后仍调用 sched + uclamp，浪费 2 次 syscall

```rust
pub fn apply_thread(...) -> ApplyOutcome {
    let mut outcome = apply_affinity(tid, pkg, policy, topo);
    // ← 若 outcome == Exited，以下两个调用无意义且每次都走完

    if let Some(pol) = policy.sched {
        if let Some(sched_outcome) = apply_sched(tid, pkg, pol, ...) {
            outcome = sched_outcome;  // 返回 Some(Exited)，覆盖
        }
    }
    apply_uclamp(tid, pkg, policy.uclamp_min, policy.uclamp_max, &mut outcome);
    outcome
}
```

线程已退出时，`apply_affinity` 返回 `Exited`，后续 `sched_setscheduler` + `sched_setattr` 都会 ESRCH，每次做了无用的系统调用。对频繁线程退出的场景（音频线程、Binder 线程）有额外开销。

**修复：** 在 `apply_affinity` 结果后加早返：
```rust
if outcome == ApplyOutcome::Exited {
    return outcome;
}
```

### 🟠 BUG-M2 `engine.rs::apply_single_tid` — `SkippedNoCpus` 不更新 `applied_tids`，sched-only 规则被反复应用

```rust
let outcome = policy::apply_thread(tid, pkg, &policy, topo, rt_allowed);
if outcome == ApplyOutcome::Exited || outcome == ApplyOutcome::SkippedNoCpus {
    return 0;  // ← applied_tids.insert(tid) 未执行
}

// 只有 Applied/Downgraded 等路径才更新 applied_tids
let state = tracker.get_mut(pid);
if let Some(s) = state {
    s.applied_tids.insert(tid);
}
```

对 sched-only 规则（`cpus = ""`），每次 ThreadClone 增量路径都不把 tid 加入 `applied_tids`。下次该 tid 再被检查时，`state.applied_tids.contains(&tid)` 为 false，重新调 `sched_setscheduler`。对 Binder 线程（每进程可有 16+ 条，频繁创建）会产生持续重复调用。

全扫路径（`refresh_process_rules`）末尾 `state.applied_tids = tid_set` 会收敛，但增量路径间隔内（TTL 2s）存在重复。

**修复：** `SkippedNoCpus` 分支也应更新 `applied_tids`：
```rust
ApplyOutcome::Exited => return 0,
ApplyOutcome::SkippedNoCpus => {
    if let Some(s) = tracker.get_mut(pid) {
        s.applied_tids.insert(tid);
    }
    return 0;
}
```

### 🟠 BUG-M3 `decision.rs::decide_ctx` — `BackgroundLatencySensitive` 被归因为 `ForegroundInteractive`

```rust
pub fn decide_ctx(&self, ctx: &DecisionContext) -> Decision {
    ...
    match ctx.intent {
        TaskIntent::Frozen => return Decision::Skip { reason: Reason::Frozen },
        TaskIntent::Background => return Decision::Skip { reason: Reason::Background },
        _ => {}  // ← BLS 和 Interactive 都到这里
    }
    ...
    Decision::Allow { reason: Reason::ForegroundInteractive }  // ← BLS 被标为此原因
}
```

`BackgroundLatencySensitive`（音频服务、后台 Binder 服务）的 `Allow` 决策被写入 audit 时，reason 为 `ForegroundInteractive`。这让 `Measure→Adjust` 闭环的决策追溯完全混乱——操作人员看到 audit 会认为这些都是前台进程干预，无法分辨 BLS 的实际行为。

**修复：** 在 `Reason` 枚举加 `LatencySensitive` 变体，BLS 路径单独返回：
```rust
if ctx.intent == TaskIntent::BackgroundLatencySensitive {
    return Decision::Allow { reason: Reason::LatencySensitive };
}
```

### 🟠 BUG-M4 `proc_source.rs` — Pending 队列对同一 pid 重复入队

`flush_pending` 使用 `std::mem::take` 清空 pending，重填保留项（retry_count 递增）。随后的全扫检查条件只验证 `!tracker.contains(pid)`，不验证 `self.pending` 是否已含此 pid：

```rust
// 全扫中，pid 不在 tracker，但已在 self.pending 的保留项里
if self.pending.len() < PENDING_MAX_PENDING
    && !self.tracker.lock()...contains(pid)
    // ← 没有检查 self.pending.iter().any(|p| p.pid == pid)
{
    self.pending.push(PendingProcess { pid, retry_count: 0, ... });
}
```

结果：同一 pid 在 pending 中出现两份（retry_count=1 的旧项 + retry_count=0 的新项）。当 cmdline 终于可读时，`flush_pending` 为同一 pid 发出两个 Fork 事件。引擎处理第二个 Fork 时会重新 `refresh_process_rules`，属冗余但不致错误。

**修复：** 加去重检查：
```rust
&& !self.pending.iter().any(|p| p.pid == pid)
```

### 🟡 分析项-L3 `decision.rs` — `Interactive + Moderate` 压力即降为 `Observe`，门槛可能过低

```rust
// evaluate(Interactive, Moderate, 0.0):
// intent_weight = 50
// pressure_mod = -15  (Moderate)
// total = 35 < 40 → Observe
```

对应测试已明确这是预期行为：
```rust
assert_eq!(e.decide(TaskIntent::Interactive, PressureLevel::Moderate), ActionLevel::Observe);
```

`Moderate` 压力对应 `avg10 > 10%`，这在 Android 日常使用中（浏览器、微信）相当常见。这意味着：**当设备处于中等内存压力时，前台游戏的 relock 会被 decide_ctx 跳过**（决策链：Interactive → Moderate → decide_ctx → evaluate → 35 < 40 → Allow{ForegroundInteractive}... 等一下）。

实际上 `decide_ctx` 里 Interactive 不会被压力降级——只有 `evaluate` 路径会。`decide_ctx` 仅检查 `pressure == Critical` 才降级。而 `relock_all` 用的是 `decide_ctx`。所以实际运行中 Moderate 不影响 relock。

但 `decide(intent, pressure)` → `evaluate(intent, pressure, 0.0).to_action(false)` 这条路径（测试 `decide_matches_evaluate_full_matrix` 覆盖的）中，Interactive + Moderate → Observe。这条路径目前在主循环没有直接使用（relock 用 `decide_ctx`），但未来接入时可能产生意外行为。这是一个**潜在语义陷阱**，而非当前 Bug。

### ✅ 确认 DeepSeek 正确：NEW-L1 (`inotify_rm_watch as u32`) 是 Claude 上轮误报

上轮审查我标记了：
```rust
unsafe { libc::inotify_rm_watch(self.fd, self.wd as u32) };
```

DeepSeek 的核查结论（`claude-P6.1-response.md` §一末尾）是正确的：libc 0.2.x crate 中 `inotify_rm_watch` 的第二参数类型即为 `u32`（Linux 上 `__u32`），不是 `i32`。`as u32` 是正确的类型转换。**Claude 上轮误报，DeepSeek 核实正确。** 当前代码的注释也已澄清此点。

### ⚠️ DeepSeek 对 NEW-H1（decide/evaluate 一致性）的终版修复带来语义变化未完整回答

DeepSeek 的 `claude-P6.1-response.md` 提出疑问："Interactive + Moderate → Observe 是否预期行为？"并请 Claude 确认。这个问题**至今未得到回答**（文件后面只有上轮 Claude 的审查，没有对这个具体问题的回复）。

我的答复：这是正确的压力感知语义，但门槛可能偏紧。Interactive 在 Moderate 压力下降为 Observe 从设计角度可接受（省电），但用户可能期望前台游戏在任何压力下都得到干预。建议把 Interactive 的 intent_weight 从 50 改为 60（Moderate 后 60-15=45>40 → 仍 Steer），仅在 Critical 压力下降级（60-40=20<40 → Observe）。这样语义更接近"前台应用优先，除非内存告急"。
