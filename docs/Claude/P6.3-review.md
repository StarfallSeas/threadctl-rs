## 二、新发现 Bug

### 🔴 BUG-H1 `policy.rs::apply_affinity` — Downgraded 路径直接调 `CpuSet::set_affinity` 而非 backend，且完全吞掉错误

这是 Backend 抽象在 `Downgraded` 路径的遗漏，同时存在错误静默问题。

```rust
// apply_affinity 步骤 ④ Downgraded 分支（当前代码）
if before != after {
    ...
    let _ = effective.set_affinity(tid);   // ← 直接调，绕过 backend
    ...                                    // ← let _ 完全丢弃返回值
    return ApplyOutcome::Downgraded;
}
```

对比步骤 ⑤（正确写法）：
```rust
match backend.set_affinity(tid, &effective) {  // ← 经 backend
    Err(errno) => { ... }  // ESRCH/EPERM/EINVAL 全路径处理
    Ok(()) => { ... }
}
```

**问题一：Backend 抽象被绕过。** `Downgraded` 是高频路径（cpuset 竞争下的缩减），未来 Backend 替换时此路径会静默使用旧实现。

**问题二：错误被完全丢弃。** 两个关键场景：

- 线程在交集计算后、setaffinity 前退出（ESRCH）：返回 `Downgraded`，调用方把这个 tid 加入 `applied_tids`、注册 cpuset dir 引用——但线程已死。下一轮 relock 才发现，且 cpuset 目录引用计数需等 cleanup 才能归零。
- EPERM（cpuset 移入失败后权限受限）：audit 写 `success: true / reason: "downgraded"`，实际 affinity 未设置，`sched_getaffinity` 读回的仍是旧值，导致下轮短路检查永远命中（`curr.bits == cpus.bits` 为 false，因为 cpus 是请求目标，不是实际值），每轮都重走这条路。

**修复：**
```rust
if before != after {
    ...
    if let Err(errno) = backend.set_affinity(tid, &effective) {
        if errno == libc::ESRCH {
            audit::record(AuditEntry { ..., success: false, reason: "esrch".into() });
            return ApplyOutcome::Exited;
        }
        // EPERM 等其他错误：记录但保持 Downgraded 语义（部分生效）
    }
    audit::record(AuditEntry { ..., success: true, reason: "downgraded".into() });
    return ApplyOutcome::Downgraded;
}
```

### 🟠 BUG-M1 `engine.rs::relock_all` — `DecisionContext.foreground` 是 oom_adj 的代理，不是真实前台状态

```rust
// relock_all 中：
let intent = TaskIntent::from_oom_adj(read_oom_adj(pid));
let dctx = DecisionContext {
    intent,
    ...
    foreground: intent == TaskIntent::Interactive,  // ← oom_adj 代理！
    audit_failure_rate: rctx.audit_failure_rate,
};
```

而 `main.rs` 每 30 秒调用一次 `refresh_foreground_uids()`，填充了 UID 级的前台缓存——但这个结果从未被 `is_foreground_uid(uid)` 提取出来送入决策路径。

`oom_adj == 0` 意味着前台（Interactive），但前台 UID 的所有进程不一定都是 oom_adj=0（例如前台游戏的 Service 进程可能是 oom_adj=200）。当前实现等价于：`foreground = oom_adj ≤ 200`，这不是真正的"当前前台应用判断"。

`from_sources(oom_adj, is_foreground, thread_hint)` 已有三源接口，只需接入：

```rust
let uid = tracker.get(pid).and_then(|s| read_uid(pid)).unwrap_or(0);
let is_fg = crate::foreground::is_foreground_uid(uid);
let intent = TaskIntent::from_sources(read_oom_adj(pid), is_fg, ThreadHint::Unknown);
let dctx = DecisionContext {
    intent,
    foreground: is_fg,
    ...
};
```

repo-overview.md 已标注 `foreground.rs` 为"⚠️ 主循环 30s 刷新，仅 debug 打印"。这个遗留项此前未进入 P6.3 计划，建议明确挂入规划或标注"P6.4"。

### 🟠 BUG-M2（P6.3 规划缺陷）`config.rs` — `cluster "little"` 在全大核 SoC 上会静默 fallback 到 Prime

P6.3 M1 修复后，SM8750/SM8850 的 detect_clusters 将返回 `Big(0-5) + Prime(6-7)`（无 Little）。但当前 config.rs 的 fallback 逻辑：

```rust
let is_valid_name = matches!(
    cluster_name.to_lowercase().as_str(),
    "little" | "big" | "prime"  // ← "mid" 也需加入（M3 后），但更大问题在 fallback
);
let found = clusters.iter().find(|c| ... == cluster_name).map(...)
    .or_else(|| {
        if is_valid_name {
            clusters.last()  // ← 最高容量集群（SM8750 上 = Prime）
                .map(|c| c.cpus.to_range_string())
        } else { None }
    });
```

用户在 SM8750 上写 `cluster "little"` → find 找不到（无 Little） → `is_valid_name = true` → fallback 到 `clusters.last()` = Prime(6-7) → **游戏主线程被绑到 2 颗 Prime 而非预期的 6 颗性能核，且没有任何警告**。

P6.3 文档说"配置报错或按 big 处理"，但代码路径给的是"静默按 prime 处理"，行为与预期不符。

**修复**：P6.3 M3 中，`is_valid_name` 判断后增加一步：若找到的 fallback cluster 不是同档位的合理近似（如 Little → Big，而非 Little → Prime），输出告警并选择 Big 而非 Last：

```rust
.or_else(|| {
    if is_valid_name {
        // fallback 策略：Little→Big，Mid→Big，Big/Prime→自身
        let fallback_kind = best_fallback(cluster_name, clusters);
        fallback_kind.map(|c| c.cpus.to_range_string())
    } else { None }
});
```

## 三、低严重度问题

### 🟡 LOW-1 `audit.rs::record` — `Vec::remove(0)` 仍是 O(n)

```rust
if log.len() >= AUDIT_LOG_MAX {
    log.remove(0);  // 每次写满都移位 255 个元素
}
```

256 个元素时每次 `remove(0)` 移位 255 次。uclamp 生效后，审计写入量上升（每次 apply 写 1~3 条），长跑影响累积。把 `AUDIT_LOG: Vec` 改为 `VecDeque`，`pop_front` O(1)，代码改动 < 10 行。

### 🟡 LOW-2 `policy.rs::forget_cpuset_dir` — 现在只是一个多余的转发层

```rust
// policy.rs
pub(crate) fn forget_cpuset_dir(dir_name: &str) {
```

### 🟡 LOW-5 `ENSURED_CPUSET_DIRS` 跨测试污染风险

`backend.rs` 中的 `ENSURED_CPUSET_DIRS` 是全局 `LazyLock<Mutex<HashSet>>>`，在测试进程内跨所有测试共享。若某个测试插入了 "0-3"，后续测试的 `ensure_dir("0-3")` 会命中缓存跳过 `create_cpuset_dir`（这实际上是好事，避免路径不存在导致 syscall 失败）。

但若测试需要验证"forget 后 ensure 会重建目录"的语义，缓存可能干扰结果。目前无此类测试，问题暂不影响 60 个测试结果，但在 P6.3 增加 topology 单测时需要注意。

## 四、P6.3 规划书审查

### ✅ 总体判断：规划合理，三个细节需确认

**设计正确的部分：**
- 运行时自动探测（cpu_capacity + cpufreq policyN/affected_cpus），坚持不做 SoC 型号硬编码 ✅
- SM8650 "容量视角 = 1+3+2+2，电压域视角 = 1+2+3+2"的区分清晰 ✅
- Mid 引入后 `big` 语义在 SM8650 上自动从 2-6 缩为 4-6 是正确的修复方向 ✅
- DVFS 域只读、仅文档化、绑核仍按 capacity cluster 的决策符合"不过度设计"原则 ✅

**需确认的细节：**

**P6.3-规划-1：全大核判定阈值"最低组容量 > 300"需真机校准**

文档描述：
> 容量比(高/低) < 2.5 **或** 最低组容量 > 300 → Big+Prime

"或"意味着任一条件成立即判全大核。问题：未来某个高效率小核（capacity=350，新一代 A520 变种）若出现在 big.LITTLE 2 组 SoC 上，`capacity > 300` 会误判为全大核。

建议改为"**且**"（AND 逻辑）：两个条件同时满足才认为是全大核，增加判定可靠性。或者仅保留"容量比 < 阈值"（更稳健），阈值由 SM8750 无设备时用单测保守定为 2.0。

**P6.3-规划-2：SM8650 容量 4 组的 Mid 边界**

文档中 SM8650 的容量分组如下：
- cpu0-1：A520（2.2GHz）= Little
- cpu2-3：A720（3.0GHz）= Mid  
- cpu4-6：A720（3.2GHz）= Big
- cpu7：X4（3.3GHz）= Prime

cpu2-3 和 cpu4-6 都是 A720，只是频率档不同（3.0 vs 3.2GHz），cpu_capacity 可能极为接近。如果 OEM 把 2-3 和 4-6 设为同一 capacity 值（SoC 厂商在 board 文件里有自由度），detect_clusters 会把它们合并为同一组，导致 N=3（而非 N=4），Mid 判定不生效，cpu2-3 并入 big。

M4 真机验证需要特别确认 `cat /sys/devices/system/cpu/cpu{2,3,4,5,6}/cpu_capacity` 返回值是否真正不同。

**P6.3-规划-3：DVFS 域读取路径与 affected_cpus vs related_cpus**

规划书使用 `affected_cpus`（`/sys/devices/system/cpu/cpufreq/policyN/affected_cpus`）。注意：
- `affected_cpus`：当前频率域内在线 CPU 的子集
- `related_cpus`：完整频率域（含离线 CPU）

对离线 CPU 的 DVFS 域分析，`related_cpus` 更完整。建议 M2 实现时优先读 `related_cpus`，fallback 到 `affected_cpus`（保持鲁棒性）。
