## 二、新发现 Bug

### 🔴 NEW-H1 `policy.rs` — `ENSURED_CPUSET_DIRS` 缓存被 Backend 重构破坏，每次 apply 都重写 cpuset 目录

这是 Backend 重构引入的性能回归，影响每个 relock 周期。

**旧代码（有缓存）：**
```rust
fn ensure_cpuset_dir(topo: &CpuTopology, dir_name: &str) {
    if let Ok(mut guard) = ENSURED_CPUSET_DIRS.lock() {
        if !guard.insert(dir_name.to_string()) {
            return; // 已确保过，直接返回
        }
    }
    create_cpuset_dir(&path, dir_name, &topo.mems_str); // 只做一次
}
```

**新代码（backend.ensure_dir，无缓存）：**
```rust
fn ensure_dir(&self, name: &str) {
    let path = format!("{}/{}", BASE_CPUSET, name);
    crate::topology::create_cpuset_dir(&path, name, "0"); // 每次都调
}
```

`create_cpuset_dir` 每次执行：`libc::mkdir`（EEXIST 快返）+ `libc::chmod` + `libc::chown` + `fs::write(cpus)` + `fs::write(mems)`。前三项虽然快，但在 SM8550 真机上 100 个线程 × 每次 relock = 每轮 400+ 不必要的 syscall/文件写入。

现状：`ENSURED_CPUSET_DIRS` 这个 `HashSet` 仍然存在于 policy.rs，`forget_cpuset_dir` 还在删除它里面的条目，但**没有任何地方向它插入内容**了。它是一个永远为空、徒占锁资源的死数据结构。

**修复方案**：把缓存逻辑移入 `LinuxV1Backend::ensure_dir`：
```rust
fn ensure_dir(&self, name: &str) {
    // 加回缓存检查（原 ENSURED_CPUSET_DIRS 逻辑）
    if !crate::policy::try_insert_cpuset_dir(name) {
        return;
    }
    let path = format!("{}/{}", crate::topology::BASE_CPUSET, name);
    crate::topology::create_cpuset_dir(&path, name, "0");
}
```
或者在 policy.rs 的调用处包一层缓存判断。同时把 `ENSURED_CPUSET_DIRS` 的 insert 路径接回来，或彻底删掉死结构。

### 🟠 NEW-M1 `backend.rs::set_uclamp` — 死赋值 + 语义模糊

```rust
const UCLAMP_MIN: u64 = 0x20;
const UCLAMP_MAX: u64 = 0x40;
attr.sched_flags = (UCLAMP_MIN | UCLAMP_MAX)
    | if min.is_some() { 0 } else { 0 }  // ← 两分支相同，纯噪音
    | 0;                                   // ← 或 0，无效
// 下一行立即覆盖上面的结果
attr.sched_flags = UCLAMP_MIN | UCLAMP_MAX;  // ← 第一行赋值完全无效
```

第一行是重构残留（原本打算按 min/max 分别设 flag，后改为始终同时设），留下了死代码。`clippy` 应该会标记这个 `let _ = a | if x { 0 } else { 0 } | 0` 模式。

附带语义问题：当用户只配了 `uclamp_min = 700`（无 uclamp_max），代码设 `sched_util_max = None.unwrap_or(1024) = 1024` 并同时发出 `SCHED_FLAG_UTIL_CLAMP_MAX` 标志。这会把内核里已有的任何自定义 max 重置为 1024（等同于"无上限"）。意图可能是合理的（未指定 = 不约束），但应该有注释说明，不然看起来像 bug。

**修复**：
```rust
attr.sched_flags = if min.is_some() { UCLAMP_MIN } else { 0 }
                 | if max.is_some() { UCLAMP_MAX } else { 0 };
attr.sched_util_min = min.unwrap_or(0).clamp(0, 1024);
attr.sched_util_max = max.unwrap_or(1024).clamp(0, 1024);
```

### 🟠 NEW-M2 `policy.rs::apply_sched` — `ret_result` 是无意义的中间变量

```rust
let ret = backend.set_scheduler(tid, policy, rt_prio);  // Result<(), i32>
// ... set_nice ...
let ret_result: Result<(), i32> = ret.map(|_| ());  // ← map Ok(()) to Ok() = no-op!
let ret = match ret_result {
    Ok(()) => 0,
    Err(e) => e,
};
```

`set_scheduler` 已经返回 `Result<(), i32>`。`ret.map(|_| ())` 把 `Result<(), i32>` 映射到 `Result<(), i32>`，完全不变，是一个 no-op。然后 `match` 把它拆回 `i32`。这是从 `if sched_setscheduler() == 0` 改为 backend 调用时的重构痕迹，没有清理干净。

**修复**：
```rust
if let Err(errno) = backend.set_scheduler(tid, policy, rt_prio) {
    if errno == libc::ESRCH { return Some(ApplyOutcome::Exited); }
    if warn_once(...) { eprintln!(...); }
    audit::record(...);
    return Some(ApplyOutcome::BlockedByPerm);
}
None
```

### 🟠 NEW-M3 Backend 抽象不完整：`attach_task` 和 `forget_dir` 是死代码

**`CpusetOps::attach_task` 从未被调用：**

```rust
// backend.rs 里存在：
fn attach_task(&self, tid: i32, dir: &str) {
    let _ = fs::OpenOptions::new()...  // 静默吞掉错误
}

// 但 policy.rs 里仍然直接写（为了 warn_once + audit 错误处理）：
if let Err(e) = fs::OpenOptions::new().append(true).open(&tasks)...
```

`policy.rs` 的直接写是合理的（需要 `warn_once + audit`），但这意味着 `attach_task` 在 `CpusetOps` trait 里是死方法。

**`CpusetOps::forget_dir` 造成循环依赖：**

```rust
// backend.rs:
fn forget_dir(&self, name: &str) {
    crate::policy::forget_cpuset_dir(name);  // ← 调回 policy.rs
}
```

而 `tracker.rs` 直接调 `crate::policy::forget_cpuset_dir(dir)`，完全绕过 backend。`forget_dir` 在 backend 里是死方法（没有调用者），且与 policy.rs 之间有反向依赖。

### 🟡 NEW-L1 `policy.rs` — `ENSURED_CPUSET_DIRS` 是死数据结构，应清除

上述 NEW-H1 的附属问题。这个 `HashSet` 现在：
- 启动时为空
- `forget_cpuset_dir` 从中删除（删不存在的 key，no-op）
- 没有任何地方插入

占用一个 `LazyLock<Mutex<HashSet<String>>>` 的持续内存和锁。要么修复（把 insert 接回来），要么删除。

### 🟡 NEW-L2 `uclamp_supported()` — Relaxed 原子排序不够

```rust
UCLAMP_SUPPORTED.store(supported, Ordering::Relaxed);
UCLAMP_CHECKED.store(true, Ordering::Relaxed);
```

两个 `store` 用 Relaxed 排序，CPU/编译器可以重排，理论上另一个线程可能看到 `CHECKED=true` 但 `SUPPORTED` 还是旧值。

实际上当前 daemon 主循环是单线程，不会触发此问题。但 P4 规划有 `--parallel` worker 线程，届时这会是真正的 race。用 `OnceLock<bool>` 替代两个原子变量是最简洁的正确方案：

```rust
static UCLAMP_SUPPORT: OnceLock<bool> = OnceLock::new();
fn uclamp_supported() -> bool {
    *UCLAMP_SUPPORT.get_or_init(|| { ... })
}
```

### 🟡 NEW-L3 `LinuxV1Backend::ensure_dir` 硬编码 `mems = "0"`

```rust
fn ensure_dir(&self, name: &str) {
    crate::topology::create_cpuset_dir(&path, name, "0");  // ← 总是 "0"
}
```

旧的 `ensure_cpuset_dir(topo, dir_name)` 用 `&topo.mems_str`（从 `/dev/cpuset/threadctl/mems` 读取）。Backend 不持有 topology，所以硬编码了。Android 是单 NUMA 节点，mems 始终是 `"0"`，实际影响为零，但这是语义上的简化，若未来支持多 NUMA 需改。

## 三、DeepSeek Q4-Q6 答复

**Q4（Backend `&self` 零大小设计）**：正确，当前 `LinuxV1Backend` 是零大小类型，`&self` 无额外开销。若未来 Backend 需要携带状态（`base_cpuset_fd`、`mems_str`），需要把字段加入 struct 并在 daemon 初始化时传入，不需要改 trait 签名。暂不引入 `Arc<dyn TaskBackend>`，动态分发开销和生命周期复杂度不值得。

**Q5（attach_task 收敛）**：推荐方案是把 `CpusetOps::attach_task` 改为返回错误，让 policy.rs 能用它并在调用处做 `warn_once + audit`。否则 trait 里有死方法，维护负担高于收益。简单改法：
```rust
fn attach_task(&self, tid: i32, dir: &str) -> Result<(), std::io::Error>;
```
然后 policy.rs 用它并处理错误，`fs::OpenOptions` 逻辑移入 `LinuxV1Backend::attach_task`。

**Q6（ensure/forget 重复）**：这直接关联 NEW-H1。统一方案：把缓存 (`ENSURED_CPUSET_DIRS`) 的 insert 移到 `LinuxV1Backend::ensure_dir` 里；`forget_dir` 直接调 policy.rs 的 `forget_cpuset_dir`（或把缓存移到 backend struct 字段，但这需要 backend 有状态）。`CpusetOps::forget_dir` 的循环依赖消除方法：在 trait 层删掉该方法，tracker.rs 继续直接调 `policy::forget_cpuset_dir`。

## 四、ChatGPT 终审问题答复

**问题 1（Backend 与 DecisionEngine 边界）**：边界正确。`policy.rs` 持 `&LinuxV1Backend`（具体类型而非 trait object），这对当前单 backend 场景是最优解。若未来需要多 backend 运行时切换，推荐在 daemon 层用泛型而非 `Arc<dyn TaskBackend>`：`fn handle_events<B: TaskBackend>(...)` 让编译器单态化，零动态分发开销。

**问题 2（MERGE_TABLE 与 Backend 分离）**：正确。约束合并语义（uclamp Max/Min）在 merge.rs，执行在 backend.rs，两个关注点分离清晰。未来若 cpu.weight、io.weight 进入 Policy，只需在 MERGE_TABLE 加行 + Policy 加字段，不动 backend 接口设计。

**问题 3（Zygote 3 次重试）**：总等待 100+300+1000=1400ms，覆盖常规场景。SM8550 重负载下 Zygote fork 到 cmdline 就绪通常 200-800ms，1400ms 有足够余量。全扫兜底（每 2s 一次）处理极端情况。不需要延长，但可以把 1000ms 改为 2000ms 作为最终保障。
