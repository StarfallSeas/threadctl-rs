### 🟡 NEW-L2 cluster 名称匹配依赖 Debug 格式，存在潜在脆弱性

```rust
// config.rs:519
.find(|c| format!("{:?}", c.kind).to_lowercase() == cluster_name.to_lowercase())
```

`CpuClusterKind::Mid` 的 `{:?}` 是 `"Mid"`，`.to_lowercase()` = `"mid"` — 当前工作正确。但这个匹配依赖 Rust 编译器自动派生的 Debug 格式，若日后有人把变体改名（如 `MidCores`）或手写 `Debug` impl，config 里的 `cluster "mid"` 会静默失效。

**建议**（可在 P6.4 或顺手修复）：给 `CpuClusterKind` 加一个显式名称方法：
```rust
impl CpuClusterKind {
    pub fn config_name(&self) -> &'static str {
        match self {
            Self::Prime => "prime", Self::Big => "big",
            Self::Mid => "mid",     Self::Little => "little",
            Self::Unknown => "unknown",
        }
    }
}
```
config.rs 改为 `.find(|c| c.kind.config_name() == cluster_name.to_lowercase())`。

## 七、DeepSeek 三个问题的回复

**Q1：N≥5 中核规则（仅第一中间组=Mid）是否足够？**

对当前所有目标 SoC 完全足够：
- SM8475/SM8550/SM8750/SM8850：N=2或3，不涉及此路径
- SM8650：N=4，第一中间组=Mid，其余=Big，正好符合 A720@3.0(Mid) + A720@3.2(Big)

若 8 Gen 4 采用 2+2+4 五组布局，第二中间组目前会标为 `Big`（capacities 低于真正 Big）。届时可考虑：
- 方案 A：增加 `Mid2` 变体（破坏 API 但语义清晰）
- 方案 B：Mid 携带 index（`Mid(u8)`），config 用 `cluster "mid-0"` / `"mid-1"` 区分

**不阻塞 P6.3，P6.4 视 8 Gen 4 实际发布情况决策。**

**Q2：BUG-M2 fallback little/mid→big 在 SM8750 上是否可接受？**

可接受，设计正确。SM8750 上 Big(0-5) 是 6 颗 Oryon，性能低于 Prime(6-7) 但远高于任何"little"预期。用户写 `cluster "little"` 的语义是"低功耗组"，在全大核 SoC 上最接近语义的选择就是容量较低的 Big 组，不应该是 Prime（2 颗核 + 最高功耗）。

**不需要可配置 fallback 目标**——fallback 语义目标本身（同档近似）是确定的。配置化只会增加用户心智负担。告警消息已清晰，用户想要精确控制时可直接用 `cpus "0-5"`。

**Q3：detect_dvfs_domains related/affected fallback 顺序是否完备？**

完备。实现与 Claude P6.3-规划-3 建议完全一致：
```rust
let raw = fs::read_to_string(format!("{base}/related_cpus"))
    .or_else(|_| fs::read_to_string(format!("{base}/affected_cpus")))
    .ok();
```

SM8550 真机验证 `[0-2, 3-6, 7]` 与容量分组完全吻合，说明 `related_cpus` 路径可正常工作。`affected_cpus` fallback 覆盖了某些内核不提供 `related_cpus` 的情况（如部分旧版 Android 内核）。
