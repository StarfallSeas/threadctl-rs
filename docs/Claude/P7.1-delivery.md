## 新发现

### 🟡 NEW-L1 `initial_scan` 与 `drain()` 存在启动期重复 Fork 窗口

```
try_new()            ← tracepoints 已 attach，ringbuf 开始接收事件
  ↓                     （真实 fork 开始进 mpsc 缓冲）
on_config_changed()  ← 白名单填入
  ↓
第一次 poll():
  initial_scan()     ← 扫 /proc，为所有已运行白名单进程发 Fork 事件
  drain()            ← 消费 mpsc，其中包含 initial_scan 期间产生的同一批进程的 fork 事件
```

两者对同一 pid 各发一次 Fork。Engine 的 `tracker.enter()` 是幂等的，第二次 Fork 触发多余的 `refresh_process_rules`，不影响正确性，但有冗余 syscall。

**当前可接受**，属已知设计取舍。若需消除，可在 `initial_scan` 写入 tracker 前标记，后续 drain 跳过已记录 pid。

### 🟡 NEW-L2 `remove_tid` 单测仅覆盖 happy path，两个 no-op 分支未测

```rust
pub fn remove_tid(&mut self, pid: i32, tid: i32) {
    if let Some(state) = self.procs.get_mut(&pid) {  // pid 不存在 → 静默跳过，未测
        state.applied_tids.remove(&tid);              // tid 不在集合 → 静默跳过，未测
    }
}
```

这两个分支都是正确的（HashSet::remove 对不存在的 key 幂等），但在 EXIT 事件乱序时会走到这里，建议补充：

```rust
#[test]
fn remove_tid_nonexistent_pid_is_noop() {
    let mut tracker = StateTracker::new();
    tracker.remove_tid(999, 100); // 不 panic，不改变状态
}

#[test]
fn remove_tid_nonexistent_tid_is_noop() {
    let mut tracker = StateTracker::new();
    tracker.enter(1, "com.a".into(), 100);
    tracker.record_applied_tids(1, &[101].into_iter().collect());
    tracker.remove_tid(1, 999); // tid 999 不在集合，applied_tids 不变
    assert_eq!(tracker.get(1).unwrap().applied_tids.len(), 1);
}
```

### 🟡 NEW-L4 SIGTERM 时 cpuset 目录不清理（前置遗留问题，非 P7.1 新增）

`threadctl.sh stop` 发 SIGTERM。Rust 无 signal handler，进程退出时 `StateTracker` 被 drop，但 `Drop` 没有实现 cpuset dir 清理路径（清理依赖 `remove()` 的引用计数归零，SIGTERM 时主循环直接中断，`remove()` 未被调用）。

`/dev/cpuset/threadctl/<dir>` 目录会在 daemon 重启后由下一轮 relock 正常重新使用，实际危害有限。但建议 P7.3 IPC 实现后注册 SIGTERM handler，正常 shutdown 时做 tracker 清理：

```rust
// main.rs
use std::sync::atomic::{AtomicBool, Ordering};
static SHUTDOWN: AtomicBool = AtomicBool::new(false);
unsafe { libc::signal(libc::SIGTERM, sigterm_handler as libc::sighandler_t); }
// 主循环检查 SHUTDOWN 标志，正常退出
```

## DeepSeek 四个问题的答复

**Q1：BUG-M2 的 `min(deadline, pending_min_next)` 在 pending 持续存在时功耗是否可接受？**

可接受，无忙等风险。当 pending 项都在退避等待时：
- 最短退避 100ms → 睡 100ms → 唤醒 → flush_pending 发现未就绪 → 延长到 300ms → 睡 300ms
- 三次耗尽后 pending 清空 → sleep 回归 full deadline（2s）

无连续唤醒，最差情况是三次短睡（100 + 300 + 1000 = 1.4s）后恢复正常周期。

**Q2：`initial_scan` 首次 poll 全扫 /proc 耗时是否影响 eBPF 启动即时性？**

不需要并行/分片。分析：
- 全扫 500 个 /proc 条目约 50-200ms（每条 `read_cmdline` = 一次 open+read，非阻塞）
- 期间 eBPF 事件在 mpsc 缓冲（无界，不丢弃）
- 这是一次性启动成本，不影响运行时延迟
- 并行化需要引入 thread pool 或 rayon，复杂度远超收益

**Q3：TRACKED_TGID_MAP 方案（P7.2）是否有更优替代？**

没有。分析各方案：

| 方案 | 问题 |
|---|---|
| 用户态维护 Set，内核无法查 | BPF 内核态无法读用户态内存，不可行 |
| TRACKED_TGID_MAP（BPF HashMap，内核查/用户写） | **正确方案**——BPF map 是唯一跨态共享通道 |
| 内核态查 /proc | eBPF 不能调用文件系统 API |

P7.2 实现 TRACKED_TGID_MAP 时注意：用户态在 Fork 事件确认（cmdline 就绪）后调 `target_tgid_map.insert(tgid, 1)`，进程退出清理 `target_tgid_map.remove(tgid)`。内核端 exit handler 查表，未命中则不发 EXIT 事件到 ringbuf，从根本上消除全量 EXIT 的 ringbuf 压力。

**Q4：单测 5 个是否覆盖充分？**

基本覆盖，有以下缺口（见 NEW-L2/L3）：
- `remove_tid` 缺 2 个 no-op 分支测试
- `target_entries` 缺恰好 8 字节边界测试
- `flush_pending` Tgid 分流逻辑（Tgid==Pid vs Tgid!=Pid）无测试（需要 mock /proc 或集成测试）

# 二、可视化 UI 规划

## 结论先说

**做 Web，不做 App，嵌入 daemon 本体，通过 KernelSU/Magisk WebUI 入口访问。**  
**Metric 线程监视功能应该合并进 threadctl，但分层：daemon 提供实时快照 API，历史/图表留给 Web 层。**

---

## 为什么是 Web 而不是 App

| 维度 | 模块 WebUI | 独立 APK |
|---|---|---|
| 安装 | 零成本（模块已装） | 额外 APK，用户门槛 |
| 维护 | 随模块更新，一体 | 独立发版周期 |
| 30 秒上手 | ✅ 打开 KSU Manager → WebUI | ❌ 需找到 APK 安装 |
| 功能上限 | 够用（观察/调试不需要 Native UI） | 更高，但不必要 |
| 二进制大小 | daemon +~100KB（内嵌 HTML/JS） | APK ~5MB |

KernelSU/Magisk/APatch 都支持模块声明 WebUI URL，用户在 manager 里点击即打开。**这是最低摩擦的入口。**

## 架构设计

```
threadctl (daemon)
 ├── HTTP server（localhost:7654，新增 ~150 行 Rust）
 │    ├── GET /              → 内嵌 HTML/JS bundle（include_bytes!）
 │    ├── GET /api/status    → JSON：统计、audit、relock 决策
 │    ├── GET /api/threads   → JSON：所有跟踪进程快照
 │    ├── GET /api/threads/:pkg → JSON：单包所有线程实时快照
 │    └── WS  /ws            → 推送：事件流（fork/exit/apply）
 │
 └── IPC socket（P7.3，Unix domain，CLI 入口）
      └── 与 HTTP server 共享数据源（无锁读快照）
```

```
Web 前端（内嵌，零构建步骤）
 ├── index.html（~3KB）
 ├── app.js（Preact/vanilla，~20KB gzip）
 └── style.css（~4KB）
```

**技术选择：** 后端用 Rust 的 `std::net::TcpListener` 写 200 行迷你 HTTP 服务器，或引入 `tiny_http`（crate 体积小），不引入 tokio/hyper（避免二进制膨胀）。前端用 Preact（3KB gzip）或纯 vanilla JS + CSS，`include_bytes!` 内嵌进 daemon 二进制，发布时无额外文件。

## 是否合并 Metric 功能到 threadctl？

**结论：合并数据采集层，不合并分析层。**

### 合并的部分（P7.4/P8）

```rust
// proc.rs 新增
pub fn read_processor(tid: i32) -> Option<u32> {
    // /proc/<tid>/stat 第 39 个字段（0-indexed 38）= processor
    let content = fs::read_to_string(format!("/proc/{tid}/stat")).ok()?;
    // 同 read_start_time 的 rsplit_once 解析
    content.rsplit_once(')')?.1.trim().split_whitespace().nth(36).and_then(|s| s.parse().ok())
}

// 新增 snapshot.rs
pub struct ThreadSnapshot {
    pub tid: i32,
    pub name: String,       // 从 thread_name_cache 读
    pub affinity: String,   // "0-7"
    pub running_cpu: u32,   // 实际运行核心，read_processor
    pub load_pct: u8,       // /proc/<tid>/stat utime 增量
}
```

daemon 暴露 `/api/threads/:pkg` 接口返回实时快照。**不在 daemon 端存储历史**（daemon 是长期运行的策略执行者，不应是数据库）。

### 留给 Web 层的部分

- 历史序列（前端每 1s 轮询 API，JS 维护滑动窗口 300 个样本 = 5 分钟）
- 迁移计数（前端对比前后两次快照的 running_cpu 变化）
- Affinity 变化检测（前端对比前后快照的 affinity 字段）
- 核心分布统计（前端累积 running_cpu 计数）
- 帧率关联（threadctl 不做，Metric 做）

### 分界线

```
threadctl daemon
  提供实时 API：「这一刻线程的状态是什么」
  
Web 前端 / Metric
  提供历史分析：「过去 5 分钟发生了什么」
```

**这是正确的分层**。daemon 不存历史是对的——一个 policy enforcer 不应该是 metrics DB。
