## 一、TOML 移除（KDL-only）细节

### 删除面
- `RawConfig`（serde 结构）、`ConfigModel::from_toml`、全部 `#[serde]` 属性
- 依赖：`serde` + `toml`（core Cargo.toml）；`kdl` 从 optional feature 变必选
- 默认模板：`config/threadctl.toml` → `config/threadctl.kdl`
- examples/threadctl.toml 删除；store 测试转 KDL

### 行为变更（语义收敛）
1. **非 .kdl 文件明确拒绝**：`仅支持 KDL 配置（X 不是 .kdl）；TOML 格式已移除，请使用 threadctl.kdl`
2. **app 节点裸属性 = default_policy**：`app "x" { cpus "0-3" }` ≡ `default { cpus "0-3" }`（与 profile 组合时显式覆盖模板）
3. **KDL 覆盖语义**：同包多条 default/同线程名节点 = **后写覆盖**（TOML `[[rule]]` 时代的按位或合并随格式移除——KDL 树形配置用显式节点表达）
4. **空 policy 零规则**：无任何字段的 default/thread 不产规则（占位规则仅在 has_any 判定时补——白名单语义保留）

### 收益
- 单配置格式（KDL 是唯一语法）——解析面减半
- release -200KB（serde/toml 移除）
- cluster 容错（数字范围当 cpus）保留在 policy_to_rules

## 三、进化路线（P9-P14，按价值排序）

### 🔴 P9 内核态决策（Hydra 方向，最高价值）

**现状**：事件 → ringbuf → 用户态 reader → mpsc → 主循环 → syscall 应用——延迟 ~100ms + 每事件用户态开销。

**进化**：eBPF 内直接决策——fork 事件在**内核态**完成线程名匹配 + 立即 setaffinity/uclamp（helper 调用），用户态只做：
- 策略下发（map 更新：pkg 白名单 → 线程名规则 → cpus/sched 表）
- 观测（ringbuf 只上送已应用结果，非原始事件）

**收益**：新线程绑定延迟 100ms → **亚毫秒**；用户态事件风暴消解。
**预估**：~400 行内核态（匹配表 + helper 调用）+ 用户态规则下发重构。
**风险**：eBPF 不能直接 setaffinity（无此 helper）——需内核 patch 或 bpf_trace_printk 方案——可行性需调研（AOSP kernel 的 bpf 支持面）。

### 🟠 P10 DVFS/频率感知选核（freq-control 方向）

**现状**：B2 只做跨域警告（validation 层），不参与选核。

**进化**：thermal_pressure（已采样）→ 选核时避开降频域——规则 `cluster "big"` 在 big 域降频时自动选第二优域；实时频率读 cpufreq（`/sys/.../cpufreq/scaling_cur_freq`）参与 decide()。
**预估**：~120 行（频率采样 + decision 输入）。

### 🟠 P11 库形态（affinitypool 方向）

**进化**：`threadctl-core` 的 policy/observe 拆出 `libthreadctl`（Rust crate）——应用内嵌创建"亲和线程池"（`AffinityPool::new("prime")` 创建绑 prime 核的 worker 池）。开源生态价值 > 游戏场景（游戏用 daemon，服务器/中间件用库）。
**预估**：~300 行 + 示例。

### 🟡 P12 场景配置一键套用（Hydra/Scene 方向）

**进化**：内置 game/chat/video/launcher/audio 场景 profile 表（P6.0 已有雏形）→ `threadctl apply-scene game` 一键切整套配置 + 热生效。
**预估**：~80 行（IPC 扩展 + 场景映射）。

### 🟡 P13 eBPF 事件扩展（launch-optimization 方向）

**现状**：fork/exec/exit 三个 tracepoint。

**进化**：
- `sched_process_fork` 已用；加 **sched_wakeup**（线程唤醒 → 若已应用过但被系统迁移，唤醒时重绑——对抗更快）
- **cgroup 迁移事件**（cgroup_attach_task？Android 内核支持面未知）——覆盖检测内核化（替代 5s 采样）

**预估**：~150 行内核态 + 用户态事件处理。

### 🟡 P14 系统 tuning 集成（system-tuner 方向）

**进化**：可选模块——CPU governor 切换（`scaling_governor`）、IO 调度器（`mmcblk0/queue/scheduler`）、内存（不 kill 进程，仅 swappiness/lmk 调优）——与 threadctl 的策略引擎统一配置。
**预估**：~200 行（backend 抽象已有雏形）。

## 四、架构现状（本轮后）

```
┌─ threadctl (daemon, 1.1MB) ─────────────────────────────┐
│ 事件源: eBPF (fork/exec/exit) ─┬─ ProcSource (降级)      │
│ 决策:   DecisionEngine (intent/pressure/audit)          │
│ 执行:   policy (3 层过滤 + cpuset + sched + uclamp)     │
│ 对抗:   B1 自适应周期 + D3 即时 (guard 1s)               │
│ 观测:   P8 sampler 5s + SnapshotWindow + snapshot IPC   │
│ 控制:   IPC status/dump/reload/apply/snapshot           │
│ 配置:   KDL only (app/profile/thread/thread-type)       │
└─────────────────────────────────────────────────────────┘
```

**测试**：107 单测（解析/匹配/合并/relock 状态机/窗口统计/PID 复用/IPC 白名单）
**资源**：空闲 CPU ~0%、RSS ~6MB、事件风暴 2% CPU、50-fork 无丢失
