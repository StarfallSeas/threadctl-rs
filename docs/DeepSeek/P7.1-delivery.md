## 二、Claude 审查 9 项修复明细（commit `6e0c9bb`）

### 🔴 BUG-H1 MAP 容量固定 64（已修）

**问题**：BPF HashMap 容量加载时固定，`map_max_entries("TARGET_COMM_MAP", 64)` 硬编码——
32+ 包时 insert 静默失败 → 超出容量包名的 fork/exec 事件内核态丢弃 → 退化全扫。

**修复**：`try_new(tracker, cfg)` 接收配置，按包数计算容量：
```rust
let cap = ((pkg_count * 2) as u32).next_power_of_two().max(64);
loader.map_max_entries("TARGET_COMM_MAP", cap);
```
内核端 `MAP_CAPACITY` 512→1024（兜底，注释与用户端覆盖关系明确）。
真机验证：2 pkgs → 3 entries 正确。

### 🟠 BUG-M1 FORK pending 无去重（已修）

**问题**：内核防抖允许同 pid 0.1s 内 2 事件 → 同一 child_pid 进 pending 两次 →
重复 Fork 事件（ProcSource 已有去重，EbpfSource 未移植）。

**修复**：`!self.pending.iter().any(|p| p.child_pid == ev.pid)` 去重。

### 🟠 BUG-M2 poll 休眠膨胀 pending 退避（已修）

**问题**：poll 空轮休眠到 deadline（2s）→ 100ms 的 pending 退避实际变成最差 2.1s，
Zygote 场景与 ProcSource 无差别。

**修复**：休眠至 `min(deadline, pending 最早退避时刻)`。

### 🟠 BUG-M3 EXIT 全量上报可能溢出 ringbuf（部分修复）

**问题**：EXIT 不走白名单（线程 comm 不匹配），高线程数应用 1s 内数千 EXIT →
256KB ringbuf 溢出 → 事件丢失。

**本轮**：ringbuf 256KB → **1MB**（短期缓解）。
**P7.2**：内核 `TRACKED_TGID_MAP` 粗过滤（fork 确认后插 tgid，exit 查表丢弃未跟踪）——根本修复 + 消除用户态每条 EXIT 锁 tracker 的 hotspot。

### 🟡 LOW-1 target_entries 双调用（已修）

单次调用 + 存 len。

### 🟡 LOW-2 内核 pid 字段注释错误（已修）

EXIT 的 pid 是 tgid（helper 带出），非"退出任务 pid"——注释修正。

### 🟡 LOW-3 文件头 ".bpf.o" → ELF（已修）

实际加载 bpfel-unknown-none 完整 ELF，非 .bpf.o 对象。

### 🟡 LOW-4 新代码无单测（已修）

新增 5 个单测：
- `tracker::remove_tid_clears_single_tid`（IMPL-4 核心：清单个 tid、无副作用）
- `target_entries_short_pkg` / `long_pkg_prefix_and_suffix` / `dedup_and_empty` / `multiple_pkgs`

### 🟡 LOW-5 repo-overview.md 未更新（留 P7.2）

与 P7.2 一起同步（topology 行数、event.rs、ebpf_source.rs、read_tgid）。

## 三、真机缺口 2 项（本轮发现并修复）

### 🎯 缺口 1：eBPF 模式缺启动时初始全扫（真机暴露）

**现象**：daemon 启动前已运行的白名单进程（sleep）不被应用——eBPF 只捕获
启动后的 fork，ProcSource 有 `scan_all=true` 首轮全扫，EbpfSource 没有。

**修复**：`EbpfSource::initial_scan()`——首次 poll 遍历 /proc 产 Fork 事件
（与 ProcSource scan_all 等价），日志 `ebpf initial scan: N whitelisted processes`。

**真机验证**：daemon 启动前启动 sleep → `ebpf initial scan: 1 whitelisted processes`
→ sleep 应用 `3-7`/`/threadctl/3-7` ✓。

### 🎯 缺口 2：启动脚本 daemon 被 SIGHUP 杀（部署形态）

**现象**：脚本后台启动的 daemon 在 su/Termux 会话退出后偶发死亡（无 setsid 隔离）。

**修复**：`threadctl.sh` 启动命令加 `nohup`（忽略 SIGHUP，$! 即 daemon pid）。

**验证**：脚本模式单实例稳定（pidof 计数=1）。
