## 〇、背景与目标

threadctl-rs 当前只在 **SM8550（骁龙 8 Gen 2）** 真机验证过 cluster 检测
（capacity 分组：little 280 / big 855 / prime 1024，DVFS 域 `{0-2}/{3-6}/{7}`）。

P6.3 目标：
1. **新增适配**：SM8475 / SM8650 / SM8750 / SM8850 的 cluster 自动识别
2. **理清 SM8650 架构**：1+2+3+2 布局 + 电压域（超大核 7 与 5,6 共享 VDD）
3. **修复现有检测缺口**：4 组容量（中核误标 Big）、全大核 2 组（误标 Little）
4. **引入 DVFS 域（电压域近似）探测**：为绑核策略提供频率协同信息

原则（沿用 P6.2）：
- **运行时自动探测，不做 SoC 硬编码表**——capacity + cpufreq 域，厂商魔改自动跟随
- **向后兼容**：SM8550 现有配置语义不变；新增 Mid 类型不破坏 big/prime 语义
- **电压域只读不改**：P6.3 仅探测 + 文档化；绑核策略仍按 capacity cluster

## 一、四 SoC 架构适配表

### SM8475（骁龙 8+ Gen 1）— 1+3+4 ✅ 现有逻辑已正确

| CPU | 核心 | 频率 | 容量组 | DVFS 域 |
|---|---|---|---|---|
| 0-3 | A510×4 | 2.0GHz | little | {0-3} |
| 4-6 | A710×3 | 2.75GHz | big | {4-6} |
| 7 | X2 | 3.2GHz | prime | {7} |

- 容量 3 组 → 现有 `detect_clusters`：Little(0-3) / Big(4-6) / Prime(7) ✓
- **无需改动**（仅纳入测试矩阵）

### SM8650（骁龙 8 Gen 3）— 官方 1+3+2+2 / 电压域 1+2+3+2 ⚠️ 需增强

**两种视角（必须分清）**：

| 视角 | 布局 | 依据 |
|---|---|---|
| 容量（性能）视角 | **1+3+2+2**：X4(7) + A720@3.2GHz×3(4-6) + A720@3.0GHz×2(2-3) + A520×2(0-1) | cpu_capacity 分组，4,5,6 同频同核 |
| 电压域视角 | **1+2+3+2**：超大核(7) + 大核(5,6) + 中核(2,3,4) + 小核(0,1) | 用户反馈：**5,6,7 共享 VDD，cpu4 独立** |

两视角的差异核心：**cpu4**——容量上归 big（3 颗 3.2GHz A720 之一），
电压域上归 mid（与 5,6 不同 rail）。

| CPU | 核心 | 频率 | 容量组（threadctl 采用） | DVFS 域 | 电压域 |
|---|---|---|---|---|---|
| 0-1 | A520×2 | 2.2GHz | little | {0-1} | VDD? |
| 2-3 | A720×2 | 3.0GHz | **mid** | {2-3} | VDD? |
| 4 | A720 | 3.2GHz | big | ? | **独立 VDD**（电压域视角归 mid） |
| 5-6 | A720×2 | 3.2GHz | big | ? | **与 7 共享 VDD** |
| 7 | X4 | 3.3GHz | prime | {7} | 与 5,6 共享 |

**电压域（✅ 已由用户真机验证，非待测）**：5,6,7 共享 VDD、cpu4 独立。
DVFS 域（cpufreq related_cpus）是否与电压域一致仍需设备侧读取确认
（用户已确认电压域事实本身；cpufreq policy 分组是内核接口细节）。

**threadctl 的取舍**：cluster 分组**按容量**（4-6 = big，2-3 = mid）——
这是 CPUFreq/调度的实际行为依据（同频同档）。电压域作为**辅助信息**
（DVFS 域探测 + 文档），供 P6.4 绑核优化（同域同频）参考，不参与 cluster 定义。

**两个缺口**：
1. **容量 4 组**：现有代码 `(n, i)` 中间组全标 `Big` → 2-3（中核）和 4-6（大核）
   都叫 "big"，`cluster "big"` 合并为 **2-6**——错误包含中核。
   → 需要 **Mid 类型**（Little / Mid / Big / Prime 四档）。
2. **电压域**：5,6,7 共享 VDD、cpu4 独立（用户反馈）。若真（待实测），
   DVFS 域 ≠ 电压域（cpufreq policy 通常是 4-6 一个域）→ 需 regulator 层探测。

### SM8750（骁龙 8 Elite）— 2+6 全大核 ⚠️ 需修复误标

| CPU | 核心 | 频率 | 容量组 | DVFS 域 |
|---|---|---|---|---|
| 0-5 | Oryon×6 | 3.53GHz | big | {0-5} |
| 6-7 | Oryon×2 | 4.32GHz | prime | {6-7} |

**缺口**：容量 2 组 → 现有代码 `(2, 0) → Little / (2, 1) → Big`——
全大核 SoC 被误标 **Little(0-5) + Big(6-7)**。用户绑 `cluster "little"` 会
绑到 6 颗 Oryon 大核（性能 OK 但语义完全错误，且 `big` 只含 2 颗 prime）。
→ 需要**全大核判定**：2 组时按容量比/绝对容量区分
  `Little+Big`（big.LITTLE）vs `Big+Prime`（全大核）。

### SM8850（骁龙 8 Elite 2，2025Q4）— 2+6 全大核 ⚠️ 同 SM8750

| CPU | 核心 | 频率 | 容量组 | DVFS 域 |
|---|---|---|---|---|
| 0-5 | Oryon×6 | 3.8GHz | big | {0-5} |
| 6-7 | Oryon×2 | 4.5GHz | prime | {6-7} |

与 SM8750 同构（频率提升），修复逻辑共享。

## 二、现有检测逻辑缺口分析（topology.rs）

```rust
// 当前 detect_clusters 分组：
match (num_groups, idx) {
    (1, _)         => Unknown,
    (2, 0)         => Little,   // ← SM8750/SM8850 误标（全大核无 little）
    (2, 1)         => Big,
    (_n, i) if i == _n - 1 => Prime,
    (_n, i) if i == 0      => Little,
    _              => Big,     // ← SM8650 4 组时 2-3(mid) 与 4-6(big) 都落这里
}
```

| SoC | 容量组数 | 当前行为 | 问题 |
|---|---|---|---|
| SM8475 | 3 | Little/Big/Prime | ✅ 正确 |
| SM8550 | 3 | Little/Big/Prime | ✅ 正确（已验证） |
| SM8650 | 4 | Little/Big/Big/Prime | ❌ 中核 2-3 误标 Big |
| SM8750 | 2 | Little/Big | ❌ 全大核 0-5 误标 Little |
| SM8850 | 2 | Little/Big | ❌ 同 SM8750 |

## 三、检测增强设计（detect_clusters v2）

### 3.1 分组逻辑

```text
输入：cpu_capacity 容量组（升序）+ cpufreq related_cpus（DVFS 域）+ 最低容量绝对阈值
输出：clusters[kind ∈ {Prime, Big, Mid, Little}] + dvfs_domains[]

N = 容量组数

N=1 → Unknown（同构，现有不变）

N=2 → 全大核判定：
    if 容量比(高/低) < 2.0 且 最低组容量 > 300：
        Big(低组) + Prime(高组)      // 全大核（SM8750/SM8850，Oryon 无小核）
    else:
        Little(低组) + Big(高组)      // 传统 big.LITTLE（SM8x50 前代）

N=3 → Little / Big / Prime（现有不变，SM8475/SM8550）

N=4 → Little / Mid / Big / Prime（新）
    中间两组按容量比排序：较低 → Mid，较高 → Big

N≥5 → Little / Mid×k / Big×k / Prime（通用，中间按容量分档）
```

**全大核判定依据**（CLAUDE P6.3-规划-1：用"且"非"或"，防新一代小核误判）：
- 容量比 < 2.0 **且** 最低组容量 > 300：Oryon 2+6 同架构容量比约 1.3~1.5；
  big.LITTLE 的 A5x vs A7x/X 比通常 > 2.5（SM8550: 1024/280 ≈ 3.66）
- 双条件同时满足才判全大核，避免高效小核（capacity>300 的 A5x 变种）误判
- 阈值可配置，SM8750 无设备 → 单测模拟边界校准

### 3.2 DVFS 域探测（新）— cpufreq/policyN，related_cpus 优先

```text
读取（用户建议，最简单直接；CLAUDE P6.3-规划-3 修正）：
  /sys/devices/system/cpu/cpufreq/              → policy0, policy3, policy7（每域一个）
  /sys/devices/system/cpu/cpufreq/policyN/related_cpus   → 完整频率域（含离线 CPU，优先）
  /sys/devices/system/cpu/cpufreq/policyN/affected_cpus  → 在线子集（related 缺失时 fallback）

SM8550 实测：
  policy0 → 0 1 2   （little）
  policy3 → 3 4 5 6 （big）
  policy7 → 7       （prime）

输出：Vec<CpuSet> dvfs_domains（policyN 即域入口，related/affected 即成员）

用途（P6.3 只读不改）：
1. 启动日志打印各 policy 的域成员，用户与官方规格核对
2. 文档化各 SoC 的 DVFS 域
3. 绑核策略输入（P6.4）：同域同频——避免拆域绑核
```

**SM8650 预期（按电压域已确认）**：policy 可能更粗（如 policy4→4,5,6,7 一个域），
与电压域（5,6,7 共享 + cpu4 独立）不一致——DVFS 域 = 频率联动组，电压域 = VDD rail
分组。P6.3 只需 DVFS 域（绑核同频依据），电压域仅文档记录。

### 3.3 Mid 类型连锁影响

- `CpuClusterKind` 增加 `Mid` 变体
- KDL/TOML 支持 `cluster "mid"`（新）；`big` 语义不变（= 最高非 prime 组，
  SM8650 上自动变为 4-6，修复现 bug——此前 big 含 2-3 中核）
- 文档：source-priority.md 不变（cluster 属编译期展开）；README cluster 表更新
- 单测：4 组/2 组全大核/3 组回归

## 七、风险与开放问题

1. **SM8650 电压域**：5,6,7 共享 VDD、cpu4 独立——**已由用户真机验证**。
   DVFS 域（cpufreq policyN/affected_cpus）独立探测，两者可能不一致
   （DVFS = 频率联动组，电压域 = VDD rail 分组）；P6.3 只用 DVFS 域，
   电压域仅文档记录，不影响绑核。无需 regulator 探测。
2. **全大核判定阈值**：容量比 2.5 / 绝对容量 300 为经验值，SM8750 无设备校准 →
   单测用模拟数据覆盖边界；部署后日志可调。
3. **Mid 引入的行为变化**：SM8650 的 `cluster "big"` 从 2-6 → 4-6（修复 bug），
   但已有用户配置可能依赖旧行为（绑 2-6）→ 文档醒目说明。
4. **eBPF/other SoC**：SM8750 的 2+6 无小核，`little` 语义在配置中应视为
   "低性能组"而非"小核"→ 文档措辞统一（cluster = 性能档位，非核心类型）。
